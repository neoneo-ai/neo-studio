# 3D Pose

The 3D Pose page runs 3d-pose-art's browser pose inside Neo Studio: the page runs three.js in an
iframe, and the host only serves the build, hosts the page and answers the bridge. Posing, the
timeline and the export all happen in the browser - the local service only reads and writes files.

## The pose package

The build has two landing paths, checked per request in this order, and **the data-root copy shadows
the bundled copy file for file** (which is why a freshly synced build wins):

| Landing path             | Contents                                                                                               | Where it comes from                                                         |
|--------------------------|--------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------|
| `<data root>/pose/dist/` | Full build, `*.map` included, about 16 MB                                                              | `tools\sync_pose_dist.ps1`; the 「启动设置 → 姿势仓库」 auto-sync           |
| `studio/pose_dist/`      | Minimal licensed copy, code + the two default CC0 base figures + the self-authored props, about 3.0 MB | `tools\build_pose_package.ps1`, ships with the Registry package and the exe |

What goes into the bundled copy is decided by **licence**, not by size: `models/ATTRIBUTION.md` marks
the page's default base figures `bodyMale.glb` / `bodyFemale.glb` (this project's standard male / female
bodies, built on MakeHuman Community's MPFB2 base meshes, CC0) and the self-authored `props/stick.glb` / `props/sword.glb`
(generated by `scripts/makePropGlb.mjs` from the `propKit` parts table) as freely redistributable, so they
ship. `ybot.glb` (CC0, PixelMannen's Y Bot) is no longer the page's default, so its 2.8 MB no longer ships.
Mixamo (`soldier` / `ch38` / `ch07`), the SMPL-derived bodies (`body1391` plus three thumbnails) and
the locally imported props (`arrow` / `sting-sword` / the guns, licence unconfirmed) none of them ship. The
panel's character dropdown ships only the two CC0 base figures `bodyMale` / `bodyFemale` - the whitelist in
`studio/web/pose/pose.js`. Mixamo, the SMPL-derived bodies and anything the user supplies never appear in it:
those licences are not this project's to ship, and a control that can only fail is not shipped. People who want
them register the GLB in the pose page's own local import area. The
prop registry `models/props/index.json` keeps only the two entries the package ships: listing a GLB the
package does not ship means shipping a control that can only fail, so trimming the registry and trimming the
files is one act, and the procedural props (`builtin:*`) stay available. A prop's preview image
(`models/props/preview/*.png`, rendered prop by prop by the pose repo's `npm run prop:preview`) ships only for a
prop whose registry row names a `preview` and whose PNG is actually in `dist`: a row that names a preview the dist
does not have gets its `preview` field stripped before packaging, so the panel reads "no preview" instead of a
broken image. `*.map` (4.4 MB) stays out: the build carries a single
`sourceMappingURL` and browsers fetch it only with devtools open, so shipping it only makes every user
download 4.4 MB more. The package also carries `LICENSE`, `THIRD-PARTY.md` (the upstream licence banners
terser deleted are restated there) and `MANIFEST.json` (`bytes` + `sha256` per file). Absolute
development-machine paths baked into the build (the figure registry's `sourceImage`) are scrubbed at
packaging time.

```
pwsh tools\build_pose_package.ps1                                       # take the ready build from <data root>/pose/dist
pwsh tools\build_pose_package.ps1 -Source <3d-pose-art repo root> -Build # npm run build first
pwsh tools\test_pose_package.ps1                                        # re-check the shipped package: manifest hashes, size cap, forbidden shapes
pwsh tools\sync_pose_dist.ps1 -Source <3d-pose-art repo root>           # full build into the data root (the preferred level)
```

`robocopy /MIR` mirrors `dist/` only, so the scenes the user wrote in
`<data root>/pose/scenes/` stay out of the mirror - and so do the extra GLBs that live in `pose/dist/models/`
and are not part of the source build: the sync
script parks those "files the source does not have" in a temporary directory and moves them back after
mirroring, so reinstalling the pose package never silently deletes a local file. `LICENSE` /
`NOTICE` from the source repo root land in the package next to the build (the pose package is MIT work,
so an installed copy must carry its license text and attribution). Reloading the page is enough after a
sync: the installed check runs per request, so the window does not need a restart.

Once "Startup settings → Pose repo" names the 3d-pose-art repo root, every desktop start tops this level
up in the data root with the same rules: files move only when the source is newer than the data root
(a relaunch of an unchanged repo copies nothing), files deleted by hand come back on the next start, and
the GLBs that live in `pose/dist/models/` beyond the source build are parked and restored around the mirror.
The gate and the
landing points are specified in [studio-desktop.md](studio-desktop.md), "Pose asset auto-sync".

## The pose library (pose-lib)

The library is the batch of whole scenes 3d-pose-art accumulated with their previews. On the pose-repo side
it is split into two roots - `pose-lib/`, the preset set (read-only, distributed with the repo), and
`pose-lab/`, the local writable set - and the sync merges them into one copy: the landing path stays a single
`<data root>/pose/lib/`, with a local entry winning over a preset one of the same id. It never ships in the
bundled copy - its licence rule differs from the pose package's, so `tools\build_pose_package.ps1` does not
package it - the sync script is what lands it. The whole directory is a cache: delete it and resync any time.
`scenes/` under `pose/` is what the user wrote, and stays out of the mirror.

| Landing path                          | Contents                                                                              | Where it comes from            |
|---------------------------------------|---------------------------------------------------------------------------------------|--------------------------------|
| `<data root>/pose/lib/poses/`         | One `.scene.json` per entry (`3dpose.scene/1`: people + props + view), preset + local | `tools\sync_pose_lib.ps1`      |
| `<data root>/pose/lib/preview/`       | `<id>.<tier>.png`: `clay` / `skeleton` / `silhouette` / `depth`                       | same script                    |
| `<data root>/pose/lib/index.json`     | `id / label / groups / categories / tags / path / preview / origin / charKey`         | `npm run lib -- merged`        |
| `<data root>/pose/lib/ATTRIBUTION.md` | Per-entry author / licence / source post of the preset set                            | same script (from `pose-lib/`) |

The merged index is computed in 3d-pose-art, not in the sync script: the repo merges its two indexes (a local
entry wins over a preset one of the same id, every entry carries `origin`) and writes the result through
`--out`. `-Source` points at the pose-repo root, and when the preset `index.json` or `poses\` is missing the
script exits and prints the `npm run lib -- shipped` command to run. Merged entries carry a `charKey` - the
result of the pose repo's `npm run lib:bodies` assignment - and the modal's base filter works on it: it
defaults to the canvas's current figure (the pose page opens on `bodyMale`, and the base filter follows the
model dropdown), and entries with no assignment carry no `charKey` and stay visible only under "all bases".
With "Startup settings → Pose repo" set, this level is also auto-synced on every desktop start — see
[studio-desktop.md](studio-desktop.md), "Pose asset auto-sync". Previews sync per tier:

```
pwsh tools\sync_pose_lib.ps1 -Source <3d-pose-art repo root>         # default tier: clay + skeleton + silhouette
pwsh tools\sync_pose_lib.ps1 -Source <3d-pose-art repo root> -Light  # skeleton + silhouette only: the leanest thumbnails the modal needs
pwsh tools\sync_pose_lib.ps1 -Source <3d-pose-art repo root> -All    # all four tiers, the depth previews included
```

`/MIR` mirrors `preview/` with per-tier `/XF` exclusions; a tier excluded now may already have landed from a
wider run, and `/MIR` does not clear excluded files, so the script then strips those leftovers by
`*depth.png` / `*clay.png` - a wide run followed by a narrow one leaves the library without two tiers mixed.

`poses/` and `preview/` each get two passes: the local library mirrors in with `/MIR` (which also clears last
run's leftovers), then the preset set fills in. That second pass carries `/E /XC /XN /XO`: `/E` is mandatory -
the library files all live under `poses/<group>/`, robocopy does not descend subdirectories by default, and
without it the preset set fills in nothing; `/XO` keeps the preset set from ever replacing a same-named file,
so preset entries only fill gaps and never touch what this machine already has - the file-side twin of the
merged index's "local wins on the same id".

The backend read route is `/pose-lib/{path}` alone: `index.json`, `poses/**`, `preview/*.png`,
`categories.json`, `ATTRIBUTION.md`. Each library carries its own category registry, and a local
`categories.json` is what gets synced when it exists - the preset one is the fallback only.
Its root is `<data root>/pose/lib`, every path goes through the `inside_dir` containment
check (`..`, a drive letter and an absolute path are 400), an empty path and a path naming a directory land
on `index.json`, and a missing file is 404 - an unsynced library and a missing file give the same answer,
and the modal decides by whether the index can be read (`index.json` failing means not synced), so nobody
browses an empty library. Every sync rewrites the files, so the whole prefix answers
`Cache-Control: no-cache`: a long cache would keep the index and the previews on the previous version after
a resync, and neither `index.json` nor a scene file may carry `immutable`. The library is read-only
throughout, and the only file-writing landing point on this side is the scene route `/neo_pose/scene`.

`/pose-lib` follows the same rule as `/pose-dist`: a static prefix each host registers directly, outside the
capability table, answered by the offline desktop service too. `/neo_pose/status` reports the library level:
`lib_dir` (the landing path), `lib_installed` (the index reads and entries are not empty), `lib_entries`
(the entry count), `lib_bytes` (the size of the whole directory).

## The cloud pose library (pose-cloud)

The cloud library is the same pose tree living in OSS: the scenes and preview images the preset library
accumulated. Entries keep the `pose-lib` shape, the cloud manifest format is `neo-pose-cloud/1`, and the
modal's cards, group dropdown, search and gate are one piece of code for both sources - switching source
only switches where the data comes from.

One config line drives it: `pose_index_url` in `<data root>/configs/oss_presets.json`, pointing at the
cloud tree's `<prefix>/index.json`. It is the third field of the OSS preset config, independent of
`presets` / `default_oss`. Missing means "not configured": the cloud source switches itself off and the
local library keeps working. Cloud props are named by the manifest's `props` array, and each one is
gate-checked against its licensing row in the pose repo's `public/models/ATTRIBUTION.md` - a row granting
redistribution (CC0 from Poly Haven and BlenderKit `cc_zero`, plus the self-made props) publishes, a
Royalty Free row, an unconfirmed source row, a Mixamo personal-use row and the repo's own test bench
boxes never do. Every published prop carries its prop-registry row (`dist/models/props/index.json`)
verbatim in the manifest.

| Landing path                               | Contents                                  | How it arrives                                 |
|--------------------------------------------|-------------------------------------------|------------------------------------------------|
| `<data root>/configs/oss_presets.json`     | `pose_index_url` (the cloud manifest URL) | Written once, pointing at the uploaded tree    |
| `<data root>/pose/oss_cache/_index.json`   | The cloud manifest last fetched           | Fetched by the read side                       |
| `<data root>/pose/oss_cache/poses/**`      | Scenes fetched before                     | Fetched on demand when a cloud card is clicked |
| `<data root>/pose/oss_cache/preview/**`    | Preview images fetched before             | Fetched per card by "refresh thumbnails"       |
| `<data root>/pose/oss_cache/models/props/` | Cloud prop GLBs and prop previews fetched | Fetched on demand when a cloud prop is added   |

`pose/oss_cache/` mirrors the cloud tree one for one and is treated as a cache like `pose/lib`: deletable and
rebuildable, with the cloud-relative path as the cache path. The manifest and the preview images are
cache-only - no cache means nothing, and the read side never pulls from the network inside a request:
opening the pose page or the library modal never contacts OSS, and an un-deployed cloud shows the
deployment hint instead of an empty list. Scene files and prop GLBs do fetch on a cache miss, land on
disk, and are served from there, so reopening the modal re-uploads nothing.

The three read routes live in `studio/pose_cloud.py` and share one function body between the plugin host
and the offline desktop service; each is registered in the `/neo_pose` ownership list:

| Method | Route                        | Purpose                                                                             |
|--------|------------------------------|-------------------------------------------------------------------------------------|
| GET    | `/neo_pose/cloud_status`     | Configured or not, cloud index URL and root prefix, cache state and cache directory |
| GET    | `/neo_pose/cloud_index`      | The cloud manifest from cache (cache-only, returns `{index, cached}`)               |
| GET    | `/neo_pose/cloud_file?path=` | A scene JSON, a preview image, `models/props/**` (prop GLBs and prop previews)      |

Cloud files accept only the relative paths the cloud manifest lists: `poses/<group>/<id>.scene.json`,
`preview/<...>.png` and `models/props/<file>.glb` (a prop written as `props/<file>.glb` and a prop preview as
`props/preview/<name>.png` land in the same place, and the rewrite swaps the whole prefix). Paths containing
`..`, a drive letter, an absolute path, or a leading `/` or `\` are refused with
`400` before the configuration is even consulted, and the landing path stays locked inside the cache
directory - a bad path never answers "not configured". Not configured answers `400` on the manifest and
the file route with the deployment hint (a `404` on a file the manifest does not list), a file the cloud
tree does not have is `404`, and a failed fetch is `502`. A prop GLB is validated by its `glTF` magic
before it is cached, so an error page the upstream sends as a file never lands in the props directory.
`/neo_pose/cloud_status` answers `200` in every state and says `enabled: false` - the modal builds its
controls from that flag.

Cloud entries travel the same send paths as shipped entries: a cloud card reads `/neo_pose/cloud_file`
and sends one `scene/apply`; a cloud prop lands in `models/props/` first and then travels the page's
existing `models/props/<file>.glb` fetch address, the same `prop/add` a shipped prop uses - the pose page
changes nothing for the cloud. The prop-registry route (`/models/props/index.json`) adds the props named by
the cloud manifest as registry rows: it reads only the cached manifest and never touches the network, and
each added row is marked `hidden` (the pose page's own prop panel has no "fetch the file first" step, so it
must not list props that are not cached). The page normalizes every prop GLB to 1 unit tall and multiplies
by the registry row's `scale`, restoring the grip metadata from the same row - a cloud prop without that row
is a 1-metre pistol. Cloud thumbnails are direct absolute OSS URLs (the ossutil bucket endpoint
is public-read), and a cloud card carries a "cloud" corner badge saying it is not in the local library. A cloud
prop card's preview is the same direct rule - the row's `preview` joined onto the bucket endpoint - while the GLB
it stands for keeps travelling `/neo_pose/cloud_file`: an OSS URL is for a thumbnail, never for the page's
`/models/props/...` fetch path.

The cloud tree is uploaded by `tools\pose_deploy_oss.py`: it produces the shape the read side accepts,
the manifest keeps only the entries whose files are actually on disk, and a prop publishes only when its
licensing row in the pose repo's `public/models/ATTRIBUTION.md` grants redistribution - CC0 (Poly Haven,
BlenderKit `cc_zero`) and the self-made props grant it, a Royalty Free row (commercial use only), an
unconfirmed source, a Mixamo personal-use row and the registry's `测试` / `单测` bench labels never do.
Each published prop carries its prop-registry row verbatim in the manifest. Credentials are read from
`<data root>/configs/backyard_oss.json` - the
`bucket` / `endpoint` / `access_key_id` / `access_key_secret` keys, the same names `studio/backyard.py`
reads. Precedence is command line > `OSS_*` environment variables > the config file, so a stale
`OSS_ENDPOINT` left in the shell overrides the endpoint in the file; pass `--endpoint` and `--bucket`
on the command line when the bucket cannot be reached. Nothing is uploaded by default - run it once to
see the list, add `--apply` to upload:

`--source` is the 3d-pose-art repo's shipped preset library `pose-lib/` (the one `npm run lib -- shipped`
builds). `<data root>/pose/lib/` is the merged result of `pose-lib` + `pose-lab` and its entries carry an
`origin`: `pose-lab` holds the author's experimental poses and is never published - the script refuses a
manifest whose entries carry `origin`, because the prop licensing gate only gates props, not the scene tree.
Whatever extra keys are already in the cloud are cleaned by `tools\pose_prune_oss.py`: its allow-set
reuses the upload script's file list, so every key the manifest does not name is deleted. A registry row
that names no `preview` is matched against the repo's conventional `preview/<glb stem>.png` in the prop
directory: a render that is really on disk travels with the prop into that same file list, so the next
cleanup never deletes a published preview, and a prop never published with a preview row that points at a
missing file.

Cloud prop previews are filled in by `tools\pose_prop_previews.py`: for each prop it takes the official
render from the source page its own registry row names (Poly Haven's `thumbnail_url` from
`api.polyhaven.com/info/<slug>`, BlenderKit's largest thumbnail in the `assetUrl` record, and the shipped
render under `studio/pose_dist/models/props/preview/` for the self-made props), writes `preview/<id>.png`
and adds `preview` to that manifest row. It only fills rows already in the manifest, publishes nothing for
`hidden` rows, touches the cloud with `--apply` only, and keeps the pre-change manifest in
`<out>/index.before.json`.

```
python tools\pose_deploy_oss.py --source "<pose repo>\pose-lib"                      # list + build the manifest only
python tools\pose_deploy_oss.py --source "<pose repo>\pose-lib" --props stick.glb katana.glb --apply
python tools\pose_prune_oss.py  --source "<pose repo>\pose-lib" --apply              # delete keys the manifest omits
python tools\pose_prop_previews.py                                                   # build previews + patch manifest rows
python tools\pose_prop_previews.py --apply                                           # upload previews and the manifest
```

The script prints the manifest URL to put into `pose_index_url`, which connects the read side.


## Page and static prefix

| Method | Route               | Purpose                                                                              |
|--------|---------------------|--------------------------------------------------------------------------------------|
| GET    | `/neo-pose`         | Short path: 302 to the entry page when installed, 404 with the install hint when not |
| GET    | `/pose-dist/{path}` | Package subresources (`index.html`, `assets/**`, GLB, wasm)                          |
| GET    | `/pose-lib/{path}`  | Read-only pose library serving: the index, scene files and previews                  |
| GET    | `/models/{path}`    | Origin-root path baked into the build: prop registry, GLBs, prop previews            |

The build uses `base: './'` relative imports, so the page must sit on a URL with directory depth:
only then does `./assets/x.js` resolve to `/pose-dist/assets/x.js`. Serving the page directly at the
root-level `/neo-pose` makes every subresource resolve to `/assets/*`, and the pose page cannot even
load its own modules - hence the short path is a redirect. The prefix stays out of the `/neo`
namespace (the capability table lists `/neo` routes one by one) and out of `/extensions` (the desktop
middleware stamps the whole `/extensions` tree `no-store`, which would re-send the hashed wasm on
every reload). Files in `assets/` carry a content hash and get `immutable` caching; unhashed entries
are revalidated every time. The prefix itself (`/pose-dist/`, an empty path) lands on the entry page:
typing the prefix in the address bar opens the page, the same directory convention a static server
uses. Files are looked up through both landing paths (data root, then the bundled copy), and both are
checked by `inside_dir`, so "running on the bundled copy" and "running on the data-root build" look
exactly the same in the URLs.

`.wasm` is forced to `application/wasm`: Windows reads `mimetypes` from the registry, and with
`application/octet-stream` `WebAssembly.instantiateStreaming` refuses the bytes, Draco cannot decode
the GLB, and the pose page never loads a figure.

The GLB files and registries under `dist/models/` are copied verbatim from `public/`, and the page
builds their addresses from its own directory (`src/core/appBase.js`): a root deployment resolves to
`/`, a host prefix resolves to `/pose-dist/`. vite's `base: './'` only rewrites build-time module
references, never runtime strings - a hardcoded `/models/bodyMale.glb` under a prefix hits the site root,
every figure 404s, and the viewport shows nothing but the procedural skeleton. An installed package
therefore has to sit in the whole directory under `/pose-dist/`; keeping only `assets/` is not enough.

The host answers both prefixes: `appBase.js` looks at the first URL segment, so a page under
`pose-dist` takes `/pose-dist/models/` and any other page takes the origin-root `/models/`. The prop
registry and the GLBs therefore live on one static handler mounted under two names, with the same
two-level lookup and the same in-root check. A host that mounts only `/pose-dist` answers
`/models/props/index.json` with a 404, the page reads the registry as empty, and every "add prop" and
GLB body reports failure while the page itself works - an empty registry is a missing host prefix, not
a user problem.

ComfyUI itself owns `/models` (the model-type list) and the single-segment `/models/<name>` (the file
list of one model type), so on the plugin host a single-segment path is ComfyUI's and only the
path-with-a-directory form - the registry and the props - reaches the pose handler. A page served under
`/pose-dist/` takes the prefix form on both hosts and never hits that ordering question.

## Bridge routes

| Method | Route                        | Purpose                                                                                                                                               |
|--------|------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| GET    | `/neo_pose/status`           | Install state, which landing path is live, the shipped manifest, the GLBs present, capability flags, saved scenes, bridge names, missing-package hint |
| GET    | `/neo_pose/scenes`           | Scene list (`name` / `size` / `mtime`, newest first)                                                                                                  |
| GET    | `/neo_pose/scene?name=`      | Read one scene                                                                                                                                        |
| POST   | `/neo_pose/scene`            | Write a scene (`{name, scene}`, `.tmp` + replace, atomic)                                                                                             |
| POST   | `/neo_pose/export_image`     | Store the page canvas (`{data: dataURL, name}`) into the library                                                                                      |
| POST   | `/neo_pose/export_set`       | Store a ControlNet set (`{files: [{name, data}]}`, ≤12) into the library                                                                              |
| GET    | `/neo_pose/cloud_status`     | Cloud configured or not, the cloud index URL, cache directory and cache state                                                                         |
| GET    | `/neo_pose/cloud_index`      | The cloud manifest from cache (cache-only, `{index, cached}`)                                                                                         |
| GET    | `/neo_pose/cloud_file?path=` | Serve one cloud file (a scene JSON, a preview image, a cloud prop GLB)                                                                                |

What `/neo_pose/status` reports about the landing paths and the shipped copy: `installed` (an entry page
in either level), `dist_dir` and `dist_source` (the live level - `data_root` or `package`),
`package_installed` and `package_dir`, `models_present` (the GLB file names present across both levels),
and `manifest_version` / `manifest_built` / `manifest_files` / `manifest_bytes` (the contents of the
shipped `MANIFEST.json`; empty and zero when there is no manifest).

Page and scene names go through a whitelist: an alphanumeric first character, at most 64 characters,
only `A-Za-z0-9_.-`. Subresource paths resolve symlinks and are forced inside one of the two landing paths; a URL
with `..`, a drive letter or an absolute path is `400`. Exported images land in
`output/Pose` - a subfolder of the normal output directory, the same place the library browses any other
output. A single image is de-duplicated and replies `{filename, subfolder, size}` with `subfolder` set to
`Pose`, and a set is validated file by file before any file is written, replying `{saved, count}` - one
invalid file writes nothing at all. Thumbnails, full-size previews, drag-into-node and the "⋯ → Delete"
action all resolve through that same relative `Pose` subfolder, and the panel's export toast names it.

Scenes go to `<data root>/pose/scenes/<name>.json`; they do not survive as part of what
`tools\sync_pose_dist.ps1` mirrors (the script parks the GLB files the source build does not have and moves
them back), so reinstalling the package leaves them alone.

All routes only read and write files, so the offline desktop service answers every one of them
(`_POSE` in `app/studio_caps.py`). `/pose-dist` and `/pose-lib` are static prefixes each host registers
directly and neither is a capability-table entry. `/neo_pose/import_model` is not registered at all: the
panel's character dropdown has no import control, so there is nothing for a host to answer.

## Host view and message directions

The desktop top bar's Pose tab and the home card "3D Pose" open `#/pose`; the host module is
`studio/web/pose/pose.js`. The host panel has two columns. The left is one column of the poses saved on this
machine: a search box,
the list of `pose/scenes/` archives (presets are not in it - a preset lives in the "Browse Pose Library…" modal),
the write-a-name-and-save row and the
"Browse Pose Library…" / "Load Pose" buttons. The right is the control panel: pose (canvas snapshot), character (add / remove),
props (preview cards), ControlNet export (formats + view + export) and canvas state (one read-only line);
the prop group is a grid of preview cards (the rules live in
"Prop cards and where a prop lands"). The character dropdown lists only the standard bodies — the ones
`meta/list` reports as `bodyMale` / `bodyFemale`. Every control stays disabled
until `pose:ready`, and the panel appears with it; the bridge is torn down with `pose:dispose`, so
leaving the page leaves no listener behind.

The left column lists only the poses saved on this machine (`pose/scenes/`, each row badged "local"): the preset
poses all live in the "Browse Pose Library…" modal, and this column does not line them up a second time. A row
loads that pose - it reads `/neo_pose/scene` and sends
`pose:open-scene` - with the Load Pose button kept for a typed-in name, the two sharing one load path. The search
box on top of the list filters the rows by name, a page is 120 rows and the rest sit behind
"load more (N left)". The list takes the height left in the column and the search box is the column's own row
above it: the modal's `flex: 1` / `min-width` search-field rule is scoped to `.ns-pose-libpane`, so the left
column carries only its own fixed-row rule and no control is stretched by the list's grow rule - the rows start
at the top of the column.
The right column has no preset dropdown and the panel has no "apply preset" step:
the "Browse Pose Library…" modal is a preset's only entry. The modal's base filter follows the panel's character -
switching bodies re-filters it, so what is visible is what the current body can wear.

"Browse Pose Library…" opens one modal (the asset library's shell) holding the `pose-lib` whole-scene
library. A card picks its preview by `clay → skeleton → silhouette → depth` (the rule the pose page's
`thumbOf` uses in `src/ui/libraryPanel.js`), a card with none of the four reads "no preview", and the
subtitle reports "N people · M props". A preview is rendered from the scene file itself: the pose repo clears
the stage to one figure per rig, empties the props and switches off every visible object outside those subjects
before the shot, and the card corner carries a "reference render" badge marking it a render and not a photo.
The figures in the picture are the scene file's headcount, and the toast reports what the page staged. A library
synced from before this change re-renders with `npm run build` then `npm run lib -- preview --all` in the pose
repo, followed by the sync.
The group dropdown is filled from the merged entries of the selected origin with their counts
(the `count` the index's `groups` carry is the preset set's own number, so poses this machine wrote in
`pose-lab` never show up in it), and refilling the options lands back on the picked group - "all groups"
when the origin switch drops it. The origin dropdown offers "all origins / preset (read-only) /
local (writable)"; a card's top-left corner reads "preset" or "local" (the tooltip names the library),
the count line reads "N poses (preset X · local Y) · showing Z" - an index entry with no `origin`
field counts as local. The search filters on
`label / categories / tags / id / source` (the field table 3d-pose-art's `filterIndex` uses in
`poseLibrary.js`). A scene can belong to several groups and its card lands only in the highest-ranked one -
two cards with the same id would cross wires on click. A page is 200 cards (640+ in the DOM at once breaks
both the first paint and scrolling) and the rest sit behind "load more (N left)". Clicking a card reads that
card's own file and sends one `scene/apply`, reporting "N rigs / M props"; a successful apply closes the
modal - the same implementation the left column's Load Pose and the page's own pose load use: it tops up
the skeleton count, lays the rigs out left to right and restores props by id. The modal's search, group
and origin dropdowns and load-more sit behind the same `libGate` as the left column: they stay disabled until
`pose:ready`, and the pane locks after an apply until the result comes back, because two quick clicks send
two apply calls and the second silently overwrites the first. When the library is not synced the modal shows
the sync command with a line of explanation instead of an empty grid: an empty browser is not what a library
looks like. The modal carries one more entry, "local pose file…", which takes a JSON file from this
machine through `pose:open-scene` - a file outside the library loads just the same.

## Prop cards and where a prop lands

The prop group is one card per prop, filled from the prop entries of `meta/list`: shipped GLBs, procedural
props and the props an own figure carries come first, cloud props last with their "cloud" badge. A preview
resolves two ways: the registry row's `preview` is a path relative to the props directory, read locally as
`/models/props/preview/<name>.png` and on the cloud as `<OSS base>/props/preview/<name>.png`; a procedural
prop has no registry row, so it reads the repo's conventional name `preview/builtin-<id>.png`. With no image
in either place the card says "no preview" - an `<img>` guaranteed to break is not what a missing image looks
like, and a cloud row's `preview` is not generated here: `tools\pose_prop_previews.py` writes the source
page's official render into that manifest row (see the cloud upload section above). The search box filters
the cards on `label / key`, the count line reads "N props · selected X", and a
selection dropped by the filter falls back to the first card of the filtered set.

"Add prop" sends the selected card's key; a prop name typed by hand travels the same "name → the entry in the
list" lookup (a built-in `builtin:chair`, a registry prop `glb:arrow.glb`). The panel never sends
`prop/attach`: the bone dropdown and the attach button live in the pose page's own panel, the host does not
copy them, and the page's `prop/attach` command stays in the command table. "Ground" and "Remove prop" act on
the selected row of the on-stage list, and each row names its own landing spot - a prop carried by a bone
reads "on hand_right", a free prop reads its X/Z coordinates.

The panel has no 姿势模式 / 吸附 / 轮廓线 / 主体层 checkboxes: posing starts by clicking the figure, which
makes the page enter pose mode on its own and leave it on an empty-space click, the page starts with snap
and outline off, and the figure stays visible - so the canvas state line mirrors only the character, its
count and the prop count. The ControlNet set is untouched by this: the line-art pass turns the outline
shells on and off inside the export itself. The two looks come from the page (studio grey / dark), and the
page opens grey, so once `meta/list` lands the panel puts the appearance on 暗色 and sends `look/set`; a
pose package whose list has no dark look is left alone. The shipped package's dark look draws a readable floor
grid: its grid lines are `0x6d7786` fully opaque, because the desktop window renders at `devicePixelRatio` 1, where
a 1px line is anti-aliased to about half coverage, so the colour carries the contrast and both hosts show the
same floor.

The ControlNet export view dropdown defaults to "current view": the page's `EXPORT_VIEWS.current` is `null`,
which means the export uses the live camera, so the panel exports from the framing the user already set. An
older package whose `meta/list` has no `current` leaves the dropdown on "View" and lets the page fall back to
its own default - the panel never writes a value the dropdown does not offer.

The panel offers no character import at all: the shipped package carries only the two licensed CC0 base
figures, and Mixamo / SMPL-derived bodies and user-supplied GLBs are registered in the pose page's own local
import area. The host has no entry and no route for it, so the desktop request-body cap stays where the
ControlNet set needs it —
48 MB and above (aiohttp's default accepts only 1 MB, and 12 PNGs base64-packed into one JSON trips a 413 at
the transport first), while the plugin route already runs inside ComfyUI's own 100 MB cap, keeping both sides
on the same size rule.

The page's own six-row toolbar is `fixed` over the canvas, and in a short window it covers exactly the
viewport posing needs: the bottom-left "面板：展开" button and the `T` key collapse it down to its first
row (the row height is measured at runtime, because wrapping makes the first row depend on the width),
and the state is stored in the page's own localStorage - nothing to do with the host toolbar.

Each host side panel (the pose library on the left, the control panel on the right) carries a collapse
button in its head, drawn as a two-pane sidebar glyph: this panel's pane is filled, and that filled pane
shrinks to a sliver once collapsed (the left panel's pane sits on the left, the right panel's is mirrored).
Collapsing one leaves a 34 px vertical rail - the panel name written vertically, with
the button as the way back out - and the freed column width goes wholly to the canvas; collapsing both
leaves the canvas the full width. On a phone each panel collapses to a 34 px horizontal strip that spans
the full width, and the
freed height goes wholly to the canvas, which keeps the full width and takes the whole screen when both are
collapsed. Collapsing
is a layout preference stored in localStorage under `neo_studio_pose_sides`, so returning to the page and
reopening the window land on the same layout; it is not gated by `pose:ready` or `caps.hostUi` - with a
missing package or an old package that disables every control, both panels still collapse.

| Message             | Direction   | Payload                                    | Purpose                                                       |
|---------------------|-------------|--------------------------------------------|---------------------------------------------------------------|
| `pose:ready`        | page → host | none                                       | The page finished setup; the host replies `pose:theme`        |
| `pose:theme`        | host → page | `{caps, lang}`                             | Capability flags and language: greys out unavailable controls |
| `pose:export-image` | host → page | reply port `{data, name}`                  | Ask for the canvas; the page answers with a dataURL           |
| `pose:save-scene`   | host → page | reply port `{name, scene}`                 | Ask for the scene; the page answers with scene JSON           |
| `pose:open-scene`   | host → page | `{scene}`                                  | Put a stored scene back into the page                         |
| `pose:call`         | host → page | `{action, args}` + reply port `{ok, data}` | A panel action runs one of the page's own commands            |
| `pose:state`        | page → host | `{state}`                                  | Canvas state snapshot, shown on the state line                |

Request messages carry a `MessageChannel` reply port, so one request's reply only arrives on that
port; inbound notifications are accepted only from this iframe (`event.source`) and from the host's
own origin, and any message name outside the list is dropped. The iframe sandbox is
`allow-scripts allow-same-origin allow-downloads` - no `allow-popups`, `allow-forms` or
`allow-top-navigation`.

The page-side bridge is `src/neoBridge.js` in the pose repository: it exists only when the page really
runs inside the same-origin iframe, and a standalone deployment (`npm run dev`, a static site) attaches
no listener at all. The bridge adds no capability of its own - it reuses two paths the page already
has: whole-scene serialization (save) and the clean snapshot (joints, gizmo and the reference-plane layer
are hidden before the canvas is read, the same code the Download screenshot button uses), plus
the page's own commands (apply a pose, the ControlNet render,
the canvas snapshot) - which is what the panel's `pose:call` runs. When serialization fails the page
stays silent on the reply port so the host times out with "the pose page did not answer" - it never
hands the host an error object for the host to write into its scenes directory as a scene. The contract
and the failure paths are in the pose repository's `docs/neo-studio-bridge.md`.

The prop row is a dropdown plus a name box. The dropdown shows the Chinese prop name, while the value sent
to the page has to be the propKey the page understands (`builtin:chair` for a procedural prop,
`glb:<file>` for a registry one); the name box takes a typed name and the host resolves it against the prop
list `meta/list` sends down - the Chinese names (椅子 / 凳子 / 桌子 / 木箱 / 木桶 / 大球 / 小球 / 圆柱 / 斜坡 /
单杠 / 台座 / 垫子 / 剑 / 短剑 / 长矛 / 弓 / 盾, plus every registry label), a bare id (`chair`,
`arrow.glb`, `arrow`) and the full key all land on the same entry, and a full-width bracket suffix in a
label (细剑（Sting）) resolves by the name in front of it. When the name is not on that list the panel says
plainly that the prop table has no such prop, reports what can be typed and how many entries there are, and
sends no `pose:call` - the prop definitions live in one place, inside the pose package, and the host does
not guess them.

The first row of the library modal is "source: local library / cloud library", a second axis next to the
library's own "all sources / preset (read-only) / local (writable)" filter: the local library reads
`<data root>/pose/lib`, the cloud library reads the tree in OSS. The cloud option appears only when
`/neo_pose/cloud_status` reports `enabled: true` - listing a source that cannot work is shipping a control
that only fails. On the cloud option the head line says "Cloud library: the tree in OSS, fetched files are
cached on this machine", each card carries a "cloud" corner badge (the hover text says which tree it lives
in), the count line reads "N cloud poses · showing Z", and the group and search dropdowns are rebuilt
from the cloud entries on the same rules as the local library. Cloud thumbnails are direct absolute OSS
URLs (the bucket endpoint is public-read), while local previews travel `/pose-lib/preview/`. "Refresh
thumbnails" on the cloud option fetches preview images one card at a time into the cache - each image
comes singly, 250 of them are 60 MB+, and nothing ever pulls the whole set. Clicking a cloud card reads
`/neo_pose/cloud_file?path=<cloud-relative path>` and sends the same single `scene/apply`; the own-scene
file path and the gate stay as they were. With no cloud configuration the modal shows the deployment hint
(`pose_index_url` in `oss_presets.json` plus `tools\pose_deploy_oss.py`), and a cache with no cloud
manifest shows that same hint with a toast carrying the `/neo_pose/cloud_index` error - never a wall of
fake cards.

Cloud props enter through the registry route the "add prop" control already uses: with the cloud configured
the prop grid merges a cloud prop card (corner badge "cloud", the same badge rule that marks procedural props
"procedural", shipped props "shipped pose package" and own figures "own"), keyed `glb:<bare file name>`;
choosing one makes the panel fetch
`/neo_pose/cloud_file?path=models/props/<file>.glb` into `models/props/` first, then send the page's
existing `prop/add` with the fetch address `models/props/<file>.glb` - the page changes nothing for the
cloud, and the prop fetch is one path. The Chinese labels, the registry `scale`, the grip metadata and the
preview path come from the prop-registry row the cloud manifest carries (its licensing text and source page
travel with the
entry, so a CC0 prop's attribution reads out); serving `/models/props/index.json` adds them to the registry
the page reads as `hidden` rows, and the page sizes the prop by that row - a service pistol lands at 0.28 m
and a quarter-staff at 2 m, the sizes the pose repo measured.

## What the desktop does not offer

In `/neo_pose/status`, the flags `photo3d`, `mesh`, `pano` and `lib_write` are always
`false`: photo point estimation, mesh generation, pano and library writes need 3d-pose-art's Python
sidecar (`pose_server.py`), which the desktop process does not start. The page greys those controls out
and the host exposes no route for them. Those panels already degrade through their own service probes
(`/__pose3d/ping`, `/__pose-lib/ping`): the endpoints exist only in vite dev/preview, so on a statically
served host the probes fail and the panels disable themselves with the project's existing "the answer is
not the estimation service" rule. `caps` is the host confirming that same state, not a second switch.
`lib_write` closes only the library's write side: reading needs no sidecar, the index and the files are
served by the host itself (`/pose-lib`), so the modal still lists the library and still applies a pose.

`body_import` is `true`, and it is a page-side capability: the package ships only the licence-clean CC0 base
figures (the standard male and female bodies), and the Mixamo / SMPL-derived figures are registered by the user
in the page's own local import area - neither the write nor the registration needs the sidecar. The host panel
offers only the standard bodies `meta/list` reports, so a whitelisted-out figure never shows as an option the
user can pick and watch fail; the page's built-in figure registry lists six GLB figures, and the entries beyond
the shipped pair resolve page-side, not in the panel's dropdown.

`hostUi` is `true`: the host ships its own panel (the pose library, ControlNet
export, the canvas state line) and sends it down with `pose:theme`, so the page folds away the demo
toolbar meant for standalone runs - only one set of controls is ever on screen. That chrome is hidden
before the page's first paint as well: the entry page's inline head script sets `data-host-ui` whenever
it runs inside an iframe (the same `parent !== window` predicate the bridge uses), so opening Pose no
longer shows the standalone 3d-pose-art editor for a moment and then swaps to the host layout. The
old-package fallback lives on the host: when `caps.hostUi` is not `true` the panel is disabled with a
notice to re-run `tools\sync_pose_dist.ps1`, so no button is left standing there only to idle.

## Not installed

When neither landing path has an `index.html` (no data-root sync, and `studio/pose_dist` deleted):
`/neo-pose` answers 404 with the install hint, `/neo_pose/status` reports `installed: false` with
`dist_source: ""`, and the host shows "3D Pose is not installed" with both install routes
(`tools\sync_pose_dist.ps1` for the full build, the bundled `studio/pose_dist`) and a Check again
button - no iframe, no toolbar.

When the page opens and the figure list is fine but every "add prop" fails, that is not a missing
install: the registry request (`/models/props/index.json`) came back 404 on the host, so the page read
the registry as empty. Check that path's status code in the browser's Network panel, and read
`dist_source` from `/neo_pose/status` to see which landing path is live. The bundled copy carries no
props by design (the licence rule), so props need the full build via `tools\sync_pose_dist.ps1`.

An unsynced library is a different matter, and the pose page stays usable: the whole `/pose-lib` prefix
answers 404, `/neo_pose/status` reports `lib_installed: false` with `lib_entries: 0`, and the "Browse Scene
Library…" modal shows that sync command with a line of explanation instead of an empty list - a missing
file and an unsynced library are the same 404, so the modal decides by whether the index can be read.
Both hints also name the second route: fill in "Startup settings → Pose repo" and every desktop start
tops both levels up in the data root.
