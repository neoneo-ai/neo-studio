# Canvas

Images and prompts, laid out on one canvas. The canvas page puts image nodes, prompt nodes, image-generation nodes, image-edit nodes, text-enhance and image-to-prompt nodes, video nodes and cars (the 车厢 of a laid-out 导演页 recipe) on the same zoomable, pannable board; the connections between nodes decide which prompts and reference images an 出图 or 出片 run carries, and where the finished images and clips land. The page lives in `studio/web/studio/pages/canvas/` (`page.js` is the page, with `geometry.js` / `nodes.js` / `interactions.js` / `store.js` / `history.js` / `node-types.js` under it, and the generation layer split by family: `gen.js` assembles and dispatches, `gen-state.js` the run state, `gen-catalog.js` the read-only lists, `gen-controls.js` the shared card controls, `gen-image.js` image generation and edit, `gen-video.js` the video chain, `gen-recipe.js` the 串联 and recipes, `gen-llm.js` enhance / reverse / storyboard), and one canvas's nodes and connections land in `canvas/<canvas id>.json` under the data root.

## Where this page is

- The `canvas` view of the Studio shell: the same path in the desktop window and in the plugin page (`createCanvasPage` in `studio/web/studio/studio-app.js`). "Place on canvas" in the material library and the gallery sends the picked assets here and lays them out as image nodes on a non-overlapping grid, each one sized to the image's own ratio.
- The desktop window opens this page with no ComfyUI runtime: all five `/neo_canvas/*` routes are in the canvas group of `app/studio_caps.py`, and reading and writing a canvas is a pure file layer. The generation and video runs need the execution queue, so pressing 出图 / 出片 with no queue only says "Generation needs the ComfyUI queue - start it from the ComfyUI pill in the header, then press it again": the page never starts the kernel for the user (one start takes the proxy target down from the kernel that is answering), the same rule the paint page's 出图 follows, and the button is not locked either.

## The toolbar

The toolbar is one row that never wraps: every control is an icon button, its name in the tooltip and its `aria-label`,
and the keyboard chord in the tooltip of the ones that have a shortcut. When the window is narrower than the row, the
bar scrolls sideways inside itself (no scrollbar shown) instead of dropping to a second row. A thin divider separates
the three groups.

- **Canvas group**: one button on the bar carrying the current canvas name with a chevron - this group shows no icon button. It opens a list of canvases pinned under the button: a row's name switches to that canvas, the 重命名 and 删除画布 icon buttons are tucked at the right end of every row - they fade in when the pointer enters that row and when the keyboard tabs into it (a touch build keeps them lit) - and each one acts on that row's canvas only; the last row is 新建画布. With no saved canvas the list has no rename or delete to press. Deleting a canvas asks for confirmation and takes `canvas/<canvas id>.json` with it.
- **Node group**: one 加节点 drop-down (it opens as the eight rows 加图片 / 加提示词 / 加图像生成节点 / 加图像编辑节点 / 加文本增强节点 / 加图片反推节点 / 加视频生成节点 / 添加配方, pinned under the button), then 撤销 (Ctrl+Z) and 重做 (Ctrl+Shift+Z or Ctrl+Y). The four clipboard acts stay on the keyboard: 复制选中 is Ctrl+D, 剪切选中 Ctrl+X, 复制 Ctrl+C and 粘贴 Ctrl+V, and each one takes nodes or a connection. Every row in that menu shows its icon with its name next to it (the name stays in the tooltip and the `aria-label` too). Picking a row closes the menu, and so do the 加节点 button itself, a press outside the bar and Esc. With nothing to undo or redo those two sit greyed, and a greyed one stays greyed under the pointer. 加图片 / 加视频输入 / 加音频输入 open the asset-library modal, and it opens on the 图片 / 视频 / 音频 chip of that class (the modal takes that class only - the chips are the gallery's quick filters).
- **View group**: zoom out / the current percentage / zoom in, then after a divider 适应内容 and 背景 (the dots / fine lines / blank cycle), and at the far right the save status slot (未保存 / {seconds} 秒后保存 / 已保存 / 保存失败 / 离线).

The four corner handles change this node's width and height, and the arrow keys nudge the selected nodes by 8px (40px with Shift), every step undoable.

## Material dropped onto the canvas (local files and library cards)

Dragging a file in from the file manager lands an input node by extension: images land as image nodes, clips as video-input nodes, sounds as audio-input nodes, and `.txt` / `.md` / `.csv` as prompt nodes - the text is read into `metadata.content` and nothing is uploaded. Releasing on empty ground adds: a batch of images lays out as a non-overlapping grid at the drop point, one clip, sound or text per node. Releasing on a node swaps that node's material and the rest are added as nodes. A node whose kind does not match is left alone - the material lands on a new input node of its own kind and the canvas says 「这一张节点吃的是图片 · 已另建一张视频输入」. A swapped image or video-input node first returns to its default box, then re-fits to the new file's own ratio. The node under the pointer lights up with a dashed outline: this drop swaps that node. Library cards follow the same rule - empty ground adds, a node swaps.

- Images, clips and sounds land in `input/` through the canvas's own file write (`POST /neo_canvas/upload`), which appends a counter to a name already taken, and the canvas takes the landed name - canvas previews and generation only read files in that folder. **The drop is a file operation, so it lands whether ComfyUI is running or not**: the route is registered in the desktop service's own table (`app/studio_caps.py`'s `_CANVAS`), and previews read through the offline-capable `/neo_gallery/image` family. An oversized file says 「上传失败（413）：{文件名}」 about that file alone and the rest of the batch still lands; text files are read on this machine and need no kernel.
- Text past 20,000 characters keeps the first 20,000 and says so; an extension the canvas does not take (a `.zip`) only gets 「画布不吃这个文件」 - never a node that can never render.
- The whole drop is undoable: one batch of dropped images is one undo, and a swapped node undoes the way 换图 does.

| Skill chip        | One chip with an icon and the skill name, sized to its content; opening it is the 绘画 page's shared skill popup - the left column switches to another entry of the image-generation skill list from the skills page (a freshly laid node defaults to the last one used), the right column edits this shot's main model and LoRA. The 主模型 line on the card reads that skill's config: the model name when it can be read, 「主模型：跟随技能配置」 when it cannot.                            |
| The parameter row | Ratio, long edge and count share one row, one chip each, each chip's meaning in its tooltip. Ratio and long edge default to following the skill config and the global generation settings - the chip then reads 「默认比例」 / 「长边尺寸」 - and an override shows the value in force; the ratio chip's icon is that ratio's shape. The count chip opens a pick from 1 to 8 (the backend eats at most 8 images per run).                                                                        |
| 出图              | The primary button owning the last row: a filled primary block across it. While the run is going it settles to a soft fill, with its position and width unchanged.                                                                                                                                                                                                                                                                                                                               |
| 取消任务          | Only appears while this run is queued or running; pressing it hands the dequeue to the backend and the node drops back out of the running state.                                                                                                                                                                                                                                                                                                                                                 |
| 自定参数          | The right column of that skill popup: the main model and LoRA for this shot (the form is the 绘画 page's shared model block). Empty = follow the skill's config and the global image settings. Changes write into `metadata.gen_params` on the spot (undoable, saved with the canvas) and switching skills clears the whole entry; a hand-picked main model from another family is taken back on the spot with the reason. Offline, with no model list read, those rows have nothing to lay out. |
| The status line   | "Queued" and "Generating {done}/{total}" follow that run's backend progress; when it fails the line carries the reason and the card turns red.                                                                                                                                                                                                                                                                                                                                                   |

- Every control writes into the node's `metadata` on the spot: undoable, travelling with a copied node and saving with the canvas. The chips, the buttons, the seed input and the 附加操作栏 buttons swallow the press (the browser has to deliver their click), and pressing one selects that node the way ComfyUI does - important on these cards, since a generation card and a train car are covered in controls, so a press that selected nothing left you guessing which card it landed on. Press-dragging anywhere else on a card drags that card: the segment summary, the 配方 prompt line, the reference count, the status and model lines are all drag handles, and the card's text is never picked up by the browser (`.ns-canvas-node` is `user-select: none`, and only the editing box and the seed input read back as selectable). A 正文 box and a video face the browser first: inside the 8px gate the press stays the browser's own gesture - text selection, play/pause - and only past it does the node move. A video card is covered end to end by the browser's own playback controls (seek, volume, fullscreen - dragging the bar at the bottom seeks and does not walk the card away), and it has no pressable patch of its own, so its fixed grab handle is the one at the head of the floating bar: a `span`, it skips the gate, a press drags that card right away and the whole selection with it.
- The chip menus and the skill popup's panel float on the page layer (`.ns-canvas-gen-menus`), not inside the node: the world layer carries a scale and nodes clip their own content, so putting them into either of those layers loses on both sides. Painting a node clears that layer, and a panel that was open reopens in place once the repaint lands. While a run is going its panel carries `ns-canvas-params-busy` and both columns give up their controls (a running shot does not change its parameters); finishing or cancelling the column restores them on the spot.
- The generation request carries the upstream prompts and reference images in connection order. With no usable line it says "Run a text or image line into this node first"; when that skill takes no text prompt it names the skill and asks for a reference image.
- 自定参数 lives on the node as `metadata.gen_params` (`model` / `loras`): the request carries only what this shot overrides, empty values stay out of it and the backend merges the skill config with the global image settings; the card's 主模型 line reads the set that is in force for this shot.
- Finished images fill the downstream empty image nodes in connection order; the leftovers create image nodes on the right, connected to this image-generation node, and one undo takes back every image this run laid down.
- Switching canvases or removing the source node detaches the run: the results do not write the old canvas, the page only says "The images are saved in the Output folder".
- A skill missing its API key says so and opens Skill Management to fill it; a failed submission reports "Generation failed", a finished one reports "Generated {n} images".

## The image-edit node

The canvas runs the 绘画 page image-edit chain (`type = "edit"`, laid out from 加节点 as 加图像编辑节点): this node only picks the skill and fires the run - the picture being edited and the prompt are not on the node, they come in through the lines wired into it, exactly the way an image-generation node takes them. This build ships the 常规 mode only - the 局部 brush, the 点选 clicks and the 扩图 drag box all draw on the picture itself, which a canvas card does not do; that run lives on the 编辑 page.

- The card is one row of controls and one status row: the skill chip, the image-count chip and 出图, then the progress and the failure reason. Selected, its bar is 停用 / 复制 / 删除 - no image picker, no prompt picker.
- Several images go into one run: the wired-in image nodes are the references in connection order and the first one is the picture being edited (the edit chain reads the first reference that way); an image wired in on two lines counts once. With no image wired in, 出图 only says 把要编辑的那一张图片节点连过来 and sends nothing.
- The prompt of this run is the wired-in prompt nodes joined in connection order; with none wired in, 出图 only says 把要用的提示词节点连过来 and sends nothing.
- The skill chip is the 绘画 page's own: 主模型 / LoRA left empty follow the skill config and the global image settings, and what you override lives in `metadata.gen_params`. Pick a skill that takes no reference image and 出图 only says {skill} 不吃参考图，换一张技能再编辑 and sends nothing. The target size is not pinned on the node - it follows the skill config and the global image settings.
- The request carries `skip_enhance` (the edit chain does not enhance the prompt), the same contract as the 绘画 page edit panel. Progress and the failure reason sit on the card's status row, which reads 编辑中 {done}/{total} while running, and a running run trades 出图 for a soft-tinted 取消任务.
- The result writes back the way an image-generation node writes back: the empty image nodes downstream take the pictures in connection order, and the leftovers create new image nodes on the right wired to this edit node.
- With no queue 出图 only says the queue needs starting from the ComfyUI pill in the header and never pulls the kernel; a disabled node says it is disabled. Same gate as the image-generation node's.

## The text-enhance node and the image-to-prompt node

The canvas runs the home page's two LLM chains on the board (`type = "enhance"`, laid out from 加节点 as 加文本增强节点, and `type = "reverse"` as 加图片反推节点): neither card carries content of its own - the text to rewrite and the picture to describe come in through the lines wired into them, and the finished text lands in a downstream 提示词 node. Both chains sit on the desktop self-serve capability table (`prompt_enhance` / `prompt_reverse` in `app/studio_caps.py`), so the two cards answer in the offline window: what they need is a configured local LLM, not the execution queue.

- The card is one row of controls and one status row: the text-enhance node's chip is which enhance skill to use - empty means the backend picks the chain from the input (a wired-in image goes through 反推, plain text through the default enhance), the same contract as the 提示词增强 page's chip, stored in `metadata.skill_id`; the image-to-prompt node's chip is the output language (中文 / 英文), stored in `metadata.language`. The last row is the 增强 / 反推 run button.
- The text streams onto the status row as 增强中 · {n} 字 / 反推中 · {n} 字 - the number counts the characters received so far, not steps - reported every 40 characters, because repainting the whole layer per token would freeze the typing and the dragging on the board. While a run is going the button trades for a soft-tinted 取消任务: cancelling closes that stream only, and the half-finished text in flight never lands on this canvas.
- The enhance run is the wired-in 提示词 nodes joined in connection order; with none wired in the button only says 把要增强的提示词节点连过来 and sends nothing. The reverse run takes the first enabled image node in connection order - the same order 出图 takes references - and when that node carries no material path the button only says 反推只吃素材库里的图：连一张带素材路径的图片节点过来 and sends nothing (a recipe asset is not in the Output folder, so the backend cannot resolve it).
- The finished text fills the first empty 提示词 node downstream in connection order (a disabled one and one that already has text are not landing slots); with no empty slot downstream it creates one at the node's lower right, wired to it. The whole run lands in one undo step. When the node is no longer on this canvas (undone away) the run only says 提示词已生成 and writes nothing.
- A backend that returns no text, and a stream that breaks, write the reason on the card's status row with an 增强失败 / 反推失败 toast; a missing capability flag only says the feature needs ComfyUI and points at the ComfyUI pill in the header, and the page never pulls the kernel. A disabled node says it is disabled - the same gate the image-generation node's run uses.

## The text-storyboard node

The canvas runs the director page's segment-generation chain on the board (`type = "storyboard"`, laid out from 加节点 as 加文字故事板节点): the text being split lives on this card - a topic ("a cat going on an adventure") or a whole script - and the run writes a prompt for every segment into the wired-in 车厢. The request is `/rs_recipes/director_generate_segments`, the same one the director page's "generate every segment from one text" uses; it sits on the desktop self-serve capability table (`storyboard` in `app/studio_caps.py`), so the card answers in the offline window: what it needs is a configured local LLM, not the execution queue.

- The card is the text box (`metadata.content`), a per-segment length box (`metadata.segment_seconds`, 1-3600 s - input out of that range is clamped into it) and the 生成段提示词 run button, with the run's status on the last row.
- One short line goes to the backend as a topic to expand; a text with line breaks, or longer than 60 characters, goes as a script and the backend splits it line by line.
- The finished segments are written into the wired-in 车厢 in connection order, one car per segment: with more segments than cars the trailing segments are not written, with more cars than segments the trailing cars stay untouched, and the card says 生成 {n} 段 · 链上 {m} 厢：按连线顺序一厢一段. A prompt wired into a car still wins at render time - this run writes the line the car itself carries.
- Segment lengths are written into the recipe segment (`/rs_recipes/set_segment_duration` - the director page, a re-laid train and every render read that one), and that write only exists when the car carries a recipe name: a hand-laid car has no recipe, so its segment length has nowhere to land. The write goes to the recipe file, not the canvas undo stack - to change it back, use the length box on the car's top row.
- The generated segments live on this node's own `metadata.segments` (with `metadata.segments_at`), and the card's last block is the preview of those lines - undo, copy and saving carry them. Switching canvas projects and leaving the page detach the run in flight: it writes nothing back to the old canvas.

## The video-generation node and the 车厢

The video-generation node is that image-generation card with its kind switched to video (`metadata.kind = "video"`): the four chips become the skill, the duration and the size, and the last row is the 生成视频 outlined pill beside 取消任务 - 出图 keeps the card's primary button.

## Laying a train with 添加配方

添加配方 is a row of the 加节点 drop-down: it opens a recipe picker reading `/rs_recipes/list`, each card carrying the recipe name and its overview line (段数 · 模式 · 技能 · 宽高 · 总时长). Picking a card lays that recipe on the canvas as one train - the picker closes by itself, the whole batch of nodes and edges lands in a single undo entry, and afterwards they are ordinary nodes. When the list cannot be read (offline, the recipe was never saved) the picker says so; a recipe over the column cap (24 segments) says so and lays nothing.

| What gets laid    | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                                |
|------------------| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| One car           | One 车厢 node per segment (`metadata.recipe` + `metadata.segment`), 3 cars per row (9 segments land as 3×3 and 6 as two rows of 3, lining up with the 九宫格 / 六宫格 storyboard grids of the 出视频 page), head to tail connected into chain edges (`previous car → next car`)                                                                                                                                                                           |
| Car reference     | Everything this segment stores lands directly above its own car, ordered by kind (images → reference videos → reference audios): image assets become 图片 nodes, reference videos become 视频输入 nodes and reference audios become 音频输入 nodes (5 images / 3 videos / 3 audios per car, 8 to a row), connected into it, each node carrying `metadata.asset` + `metadata.recipe`; the bar's 取用素材 / 换素材 replaces them with library files, taking as many as picked, and a swap clears that node's recipe provenance in the same step. Those nodes play the recipe's own copy through `/rs_recipes/asset` (no `input/` copy involved), and the run hands all three buckets to the backend |
| The tail          | One video-generation node per column (`metadata.chain = "train"`, `metadata.kind = "video"`), placed in the slot right after the last car; the one shared video skill and the anchor / continuity / context frames / steps / seed all live on that card                                                                                                                                                                                                         |
| Switching recipe  | Which recipe the column runs is fixed when it is laid and stored on every car, the tail only writes it out; to run another recipe, press 添加配方 again and lay a new train                                                                                                                                                                                                                                                                               |
| One edit          | The laid nodes and edges are one undo entry - undo takes the whole batch back; afterwards they are ordinary nodes: the text edits, the chips swap, a copy carries them and the canvas saves them                                                                                                                                                                                                                                                          |
| 停用 (in the bar) | The bar's first button writes `metadata.disabled`: the column run skips that car, the car dims with the 「已停用」 badge, and pressing the column run with every car disabled says one line and sends nothing                                                                                                                                                                                                                                             |

Laying says 「已铺好 {n} 段：参考素材按连线接进每一厢，出片与整列共用的技能在车尾」, the selection lands on the freshly laid cars, and the view pulls itself back onto the column (`fitView`).

A car runs the same chain, handing its references in the three groups `references.images` / `references.videos` / `references.audios`, and one material connected by two lines still counts once:

| The connected node               | What the payload carries                                                |
|---------------------------------| ------------------------------------------------------------------------|
| An image node (a canvas file)    | `{"kind": "input", "value": "sub/file.png[output]"}`                    |
| An asset node (a recipe file)    | `{"kind": "recipe", "value": "asset.png", "recipe": "RecipeName"}`      |
| A 视频输入 node (a canvas clip)  | `{"kind": "input", "value": "sub/clip.mp4[output]", "media": "video"}`  |
| A 音频输入 node (a canvas sound) | `{"kind": "input", "value": "sub/voice.mp3[output]", "media": "audio"}` |

The backend lands both classes in the input folder before the load node sees them (`_reference_name` in `studio/image_gen.py`): each is copied to `input/NeoAgent/<name>_<timestamp><ext>`. A missing recipe, a missing asset file, a name carrying a path separator or `..`, or a suffix outside that media type drops that one reference with a backend log line, and the run itself goes ahead.

## The tail and the column run

The chain is layout and order only: a car is a compact card — the segment number, that segment's duration box, its skill, where its prompt and reference material come from plus a preview of them, and no button on the card at all (停用, 复制 and 删除 all live in the bar above the node) — the edges and the disable flag are canvas state, and running stays on the 导演页's per-segment closed loop with no second execution path.

- The chain order walks from the tail upstream to the head and flips back (`segment 0 → segment 1 → … → segment N`); a cut chain stops at the segment it reached, and a loop is recognised.
- The tail's 生成视频 queues the enabled segments one after another, each one a `/neo_video_gen/run_segment` - ComfyUI's own queue runs them in submit order, each clip lands in its own downstream video slot (connected to that segment's car), and the tail lands none.
- The shared parameters exist on the tail only: the skill and the resolution chips sit on the tail card (both empty follows the recipe, picking one pins the whole column), while anchor, continuity, context frames, steps and seed are kept in the tail's 参数 window; the seed offsets by segment index (the tail's value is the starting point, `-1` means a random seed per segment). The main model, Text Encoder, VAE and LoRA overridden in the tail's skill popup live in its `metadata.gen_params`, and every segment of the column carries that same copy.
- 停用 on a car is the first button of the bar above the node and writes `metadata.disabled`: the column run skips that segment and the car dims with the 「已停用」 badge. A car is display only — 生成视频, the recipe, anchor, continuity, context frames, steps and seed all stay on the tail.
- The duration box on a car's top row sends `POST /rs_recipes/set_segment_duration` and writes only `segments[].duration_sec` - assets, samples and results stay untouched, unlike the full-overwrite `/rs_recipes/save`. The bounds are the director page's 1–3600 integer seconds, out-of-range input clamps to them before it lands, and a preset recipe is read-only (copy it first). The box locks while that segment's run is going, and a successful write repaints that car at once.

- The shared sentence appears on the tail's top row once: that row writes 「链上 {n} 段 · 启用 {m} 段 · {配方名}」, and the recipe name is the one every car of this column stores; a car writes none of it. The tail's top row and a car's top row share one layout (the same `.ns-canvas-car-head` row), so the two read identically on the canvas. Running another recipe means laying a new train with 添加配方.
- The tail's 取消任务 cancels every segment that column is running; a running column writes 「串联出片 {done}/{total}」 on the status line, and a failure keeps the backend's reason there.
- A broken chain speaks instead of running on defaults: a tail with no cars upstream says 「这台视频生成节点上游没有车厢：用「添加配方」铺一列」, and a column with every car disabled says 「链上没有启用的段」 - neither sends a request.
- The tail's parameters go through `metadata` and save with the canvas (`metadata.chain = "train"`, a disabled car's `metadata.disabled = true`); a car's `metadata.train` and a tail's `metadata.expand_mode` written by an older build read back untouched and the current build never writes them, and an older canvas without those keys is enabled and not a chain.

## Undo and saving

Undo and redo are two stacks in `pages/canvas/history.js`: the stacks record only nodes and connections, never the viewport or the background; the depth is capped at 60, and switching or creating a canvas clears them. One drag and one stretch of typing count as a single change, so one undo takes back the whole stretch.

Changes accumulate in this page's memory and land on disk 900ms after the last one, viewport and background included; leaving the page saves first. The indicator at the right end of the toolbar is whether this one landed. `canvas/index.json` is a list cache - delete it and the list is rebuilt from the canvas files; deletion only exists as the single-item route the UI offers, and nothing clears the whole `canvas/` folder.

## `/neo_canvas/*`

| Method | Route                 | What it does                                                   |
|-------| ----------------------| ---------------------------------------------------------------|
| GET    | `/neo_canvas/list`    | The canvas list (the index plus canvas files the index missed) |
| GET    | `/neo_canvas/project` | One canvas's nodes and connections (`?id=`)                    |
| POST   | `/neo_canvas/project` | Saves one canvas: the write layer refuses an unfinished JSON   |
| POST   | `/neo_canvas/rename`  | Changes the title                                              |
| POST   | `/neo_canvas/delete`  | Deletes one canvas                                             |

The backend is `studio/canvas.py`: writes go through a temporary file swap under one lock for concurrency, a node's `type` is stored exactly as the page wrote it (`image` / `text` / `gen` / `video` / `recipe` / `edit` and any face this build does not know yet keep their name, and only a missing one becomes `text`, so an older page falls back to the text face itself), and the offline desktop service answers the same group of routes, so the plugin and the offline window write the same file.
